Ryzen AI 9 HX 370 LLM benchmarks

Seven GGUF models from 9B to 120B parameters, run fully on the integrated GPU with llama.cpp (Vulkan and ROCm), compared against Ollama on the same weights where its files load in llama.cpp.

CPU: 12C/24T Zen 5 (4 Zen 5 + 8 Zen 5c), AVX-512GPU: Radeon 890M, gfx1150, 16 CUsMemory: 96 GB DDR5-5600, 128-bit, 80 GiB usable by the GPUROCm 10.2 (HIP 7.17) · Mesa 26.0.8 RADV
23.0tok/s generation, Qwen3.6-35B-A3B (fastest in llama.cpp)
14.2tok/s generation, gpt-oss-120b (117B, largest)
2.3xgeneration from MTP speculative decoding, Qwen3.8-27B
~80 GB/seffective memory bandwidth in generation, 90% of the DDR5-5600 peak

Recommended settings

Build both backends with the branch scripts and serve with Vulkan: all layers on the GPU, flash attention, and a 2048-token micro-batch for MoE models only. Check the machine first; the checks below found the problems this setup needed fixing.

./scripts/check-ryzen-ai.sh             # read-only setup check: ROCm arch, GTT size, Ollama GPU use, ...
./scripts/build-ryzen-ai-vulkan.sh      # -> build-vulkan
./scripts/build-ryzen-ai.sh             # -> build-rocm (gfx1150)

build-vulkan/bin/llama-server -m model.gguf -ngl 99 -fa on --jinja
#   + -ub 2048 -b 2048               for MoE models (Qwen3.x-A3B, GLM-4.5-Air, gpt-oss): +21-34% on 4k prompts
#   + --spec-type draft-mtp          for models with an MTP head (Qwen3.8-27B): 2.3x generation
#   + -ctk q8_0 -ctv q8_0            to halve KV cache memory for 0-2% prompt speed
build-rocm/bin/llama-server ...      # prompt-heavy work on gpt-oss-120b (-ub 2048) or Llama 3.3 70B

System: GTT raised to 80 GiB with ttm.pages_limit=20971520 on the kernel command line (default is half of RAM, too small for gpt-oss-120b or GLM-4.5-Air), powerprofilesctl set performance while benchmarking, and Ollama switched to its Vulkan runner with OLLAMA_IGPU_ENABLE=1 (without it Ollama 0.40 ignores the iGPU and runs on the CPU).

Findings

  • Generation is memory bound, so the backend barely matters for it. Every dense model reads its weights at about 80 GB/s, 90% of the 89.6 GB/s DDR5-5600 peak; Vulkan generates up to 5% faster than ROCm, and ROCm at most 2% faster (gpt-oss-120b). Expect roughly 80 / (GB of weights read per token) tok/s. gpt-oss-120b stays well below that (14 tok/s for about 3 GB per token), which points to its MXFP4 kernels being compute bound on the 16 CUs.
  • Vulkan is the better default, by a small margin. It prompts faster on the Qwen3.x and GLM MoE models; ROCm prompts faster on gpt-oss-120b (+14% at 4096 tokens) and Llama 3.3 70B (+26% at 512).
  • -ub 2048 -b 2048 helps MoE models only. It adds 21-34% to Vulkan prompt speed at 4096 tokens on the four MoE models and -6 to +3% on dense ones. ROCm prompt speed is not monotonic in -ub on MoE models (gpt-oss-120b: 290 / 239 / 425 tok/s at 512 / 1024 / 2048), and the Max+ 495 data shows the same dip at 1024.
  • MTP speculative decoding more than doubles Qwen3.8-27B. 4.6 to 10.5 tok/s. Ollama's build of the same file reaches 9.7, about twice the plain rate, so it uses the MTP head as well.
  • llama.cpp matches Ollama on generation and prompts faster, except on Qwen3.6-35B-A3B. There Ollama generates 17-20% faster. It is not the quantization (Ollama's file is the heavier one: Q6_K experts against Q5_K, same ~2.3 GiB of always-read weights); Ollama runs this architecture on its own engine, and its file does not load in upstream llama.cpp.
  • Ollama is faster on Vulkan. Its Vulkan runner generates faster than its ROCm runner on 6 of 9 models (+3% generation, +4% prompt, geometric mean), so the service now runs on Vulkan.
  • The Max+ 495 is 2.8-4.2x faster on the same models. It has twice the memory bus width (256-bit against 128-bit) and a much larger GPU.
